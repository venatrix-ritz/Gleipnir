# Changelog

Versions: 0.1.0 (2026-10-07, first tag), 0.2.0 (2026-10-08, adds the sleep clamp and its setting, below).

## 0.2.1 (2026-10-24)
- **Changed:** the clamp value is now `100000` µA (100 mA) on both nodes (it was `0` on Armada's `constant_charge_current` and `1000` on the fork's `charge_control_limit`). A reviewer of armada-os/armada#677 reports that values below 100000 make the charger draw swing between 0.2 W and 5 W and can upset simple chargers; 500000 is the lowest in the official spec. `CLAMP_DETECT` rises to match, so a limit at or below 100000 counts as ours. The verification marker records the clamp value, so an existing marker (`value=0`) no longer arms the daemon: **re-run the on-device test after updating**. Not yet verified on a Thor that 100000 still stops charging.
- **Added:** heavy logging debug build (`0.2.1-debug`). Logs detailed poll-by-poll snapshots every 30 s with charging current, voltage, temperature, limit readbacks, and specific decision reasons (`charging toward 80%`, `rate-limit wait`, `settle timer`, `discharging on battery`, etc.). Added debug instrumentation for `write_limit` timing, `ensure_released` verification rounds, and pre/post-sleep triggers. Off by default; enabled with `--debug` or `GLEIPNIR_DEBUG=1`.
- **Fixed:** kernel mismatch under FEX-Emu when the safety test was run from the Decky UI. Decky Loader runs as an x86_64 binary under FEX-Emu on ARM64 Linux, causing `uname -r` to return FEX's emulated kernel version (`6.11.0`) instead of the host kernel (`7.2.6`). This stamped `kernel=6.11.0` into `/var/lib/gleipnir/verified`, causing the native root service (`gleipnir.service`) and native status queries (Ratatoskr's `gleipnir_view.py`) to reject the marker as stale/unverified while Decky's UI reported it verified. `bin/gleipnir` now resolves the true host kernel via `hostnamectl` / `busctl` before falling back to `uname -r`, and automatically adopts any previously verified marker bearing `6.11.0` to the host kernel. Upgraded plugins now also sync `/var/local/bin/gleipnir` on Decky load.
- **Fixed:** a pre-sleep clamp was undone within seconds when the battery was at or below 77 % (2026-10-08 22:21, 64 %: the Thor slept unclamped and gained 10 points). The daemon adopted the clamp and its own "release at 77 % and below" rule fired in the same pass; the earlier tests hid it because they ran at 79 to 80 %, or the daemon was frozen first. The daemon now holds a clamp placed for a sleep until `--post-sleep` removes the sleep file after the resume (at most an hour), then applies its normal rules at the next poll. Reproduced without a sleep by running `--pre-sleep` by hand and reading the node twice a second. 5 new checks (102 pass). Verified on the Thor: slept 9.5 minutes at 60 % on a charger and woke at 60 % (counter +42 mAh, from the seconds before the sleep).
- **Added:** the sleep setting. `gleipnir --set-sleep-floor N` (root; 0 every sleep, 70 from 70 % up, 101 never) is saved in `/var/lib/gleipnir/sleep-floor` and read by `--pre-sleep`; the Decky panel shows Armada's current sleep type (read-only: change it in Armada Control) and a "Charge cap while asleep" dropdown, hidden in fake sleep, where the daemon keeps running. The default is now **0, clamp before every sleep**, so the cap always holds in native sleep; it means the Thor does not charge while asleep (the earlier build clamped from 70 % up, `GLEIPNIR_SLEEP_CLAMP_FROM`, which is now only the default when no setting is saved). `--status --json` reports `sleep_floor` and `sleep_mode`. 97 checks pass.
- **Tested:** the pre-sleep clamp also held when the Thor slept unplugged at 79 % and the charger was plugged in during the sleep (woke at 79 %, charge counter -8 mAh), and when it slept already clamped at 80 % (21 minutes).
- **Added:** `gleipnir --pre-sleep` / `--post-sleep` and `gleipnir-sleep.service` (ordered before `sleep.target`; systemd-sleep on the Thor does not run hooks from `/etc`). Just before a suspend it clamps from 70 % up (`GLEIPNIR_SLEEP_CLAMP_FROM`), with the charger in or out, writing a sleep file first so the running daemon adopts the clamp instead of undoing it; after resume the daemon applies its normal rules. Native s2idle freezes the daemon, so before this a Thor that slept at 78 % on a charger woke at 88 %. Tested on the Thor on 2026-10-08: slept at 76 % for 10 minutes on a 250 W charger and woke at 76 % (charge counter +6.8 mAh). Below 70 % the Thor still charges while asleep and can pass the cap. While clamped asleep it does not charge. 19 new checks (86 pass).
- **Fixed:** the watchdog read the size of `current_now` as charging. On the Thor on 2026-10-08 at 09:28 a game drained the battery at 1.4-1.7 A while the status still said `Charging`; 120 s after a clamp the watchdog called the limit ineffective, released, deleted the verification marker and exited. It now counts only a positive current. Test S5b reproduces it (fails on the old code, passes now; 67 checks).
- **Verified on one Thor, 2026-10-08:** clamp at 80 %, held through 18 minutes of a game and a brief charger swap, released at 77 % with the charger attached, charging resumed, re-clamped at 80 %. README and `docs/evidence.md` updated. Other builds are untested.
- **Fixed:** the safety test called a working limit a failure and left charging stopped. On the Thor on 2026-10-08 the node still read the old value 1.5 s after the clamp was written and the effect arrived about a minute later; the test judged the instant readback, restored in the middle of it, and the clamp then took hold with the restore not holding. Now: writes are judged by waiting for the node (`GLEIPNIR_APPLY_WAIT_S`, 120 s); the test waits up to 180 s for charging to stop and up to 120 s for it to resume, stopping as soon as it sees the result; a restore must stay in place for `GLEIPNIR_HOLD_S` (20 s) and is written again if a clamp lands after it; `--restore` and every release do the same; the daemon records a clamp before writing it (a TERM in between used to leave it in place) and undoes a clamp it did not make (`LATE CLAMP`). New tests simulate a battery whose effect lags the limit, a late clamp, and a node that shows writes late and drops writes while one is pending (61 checks).
- **Added:** monitoring for a release that does not bring charging back: a warning (`NOT CHARGING with the limit released`) when nothing is clamped, a charger is attached, the battery is below the release point and the status is not `Charging` for five polls. Found on the Thor on 2026-10-08: after the armed daemon held a clamp at 80 % for about 90 s and was stopped, the node was restored at once but the status stayed `Not charging` for more than ten minutes. The cause is not established; whether charging resumes by itself below 77 % is untested.
- Initial release (2026-10-07): Decky plugin plus the `gleipnir` daemon, status report, safety test and restore command. Watch-only until a measured test passes on the running kernel; restores on every exit; read-back of every write; watchdog for an ineffective limit; journal logging with battery snapshots and a heartbeat.
- Review hardening before publishing: the test only writes the limit back if it clamped it, refuses while the service is running, and lists every power supply when it refuses; a failed test start in the backend puts the daemon back.
- Full documentation under `docs/`.
- Tests: a simulated-battery suite for the daemon (47 checks) and a fake-runner suite for the backend (8 checks); both also pass on the Thor's own Linux userland.
